# UDS 컴포넌트 점검

## 원칙

> **화면에서 눈에 보이는 모든 관계는, 코드에서도 프로그램적으로 표현되어야 한다.**

Figma는 위치와 모양만 표현한다. "이 라벨이 저 입력의 이름이다", "이 메시지가 저 입력을 설명한다" 같은 **관계**는 Figma에 그릴 수 없다.

따라서 Figma를 기준으로 생성된 코드에는 예측 가능한 편향이 있다.

- **속성(variant, size, color)은 거의 빠지지 않는다** — Figma에 그려져 있으므로
- **관계(htmlFor, aria-describedby, aria-controls)는 체계적으로 빠진다** — Figma에 없으므로

이 스킬은 그 누락을 잡는다. 개별 실수가 아니라 파이프라인의 구조적 결함을 다룬다는 점을 기억할 것.

## 금지 표현

점검 결과나 생성 지시에 다음 표현을 쓰지 않는다.

- "시맨틱하게 만들었습니다"
- "접근성을 고려했습니다"
- "베스트 프랙티스를 적용했습니다"

검증 불가능한 진술이다. 반드시 **어떤 속성이 어느 줄에 있는지**로 답한다.

---

## 작업 흐름

### 1. 대상 파악

컴포넌트가 무엇인지 확인하고, 아래 표에서 해당 패턴 파일을 **읽는다**.

| 컴포넌트 | 읽을 파일 |
|---|---|
| Button | `patterns/button.md` |
| ButtonGroup | `patterns/button-group.md` |
| CTA | `patterns/cta.md` |
| Checkbox | `patterns/checkbox.md` |
| Radio | `patterns/radio.md` |
| Chip | `patterns/chip.md` |
| ChipGroup | `patterns/chip-group.md` |
| TextField | `patterns/text-field.md` |
| Header | `patterns/header.md` |

목록에 없는 컴포넌트라면 이 SKILL.md의 공통 체크리스트만 적용하고, **패턴 파일이 없다는 사실을 사용자에게 알린다.** 그리고 W3C WAI-ARIA APG에서 해당 패턴을 찾아 새 패턴 파일을 만들자고 제안한다.

여러 컴포넌트를 한 번에 요청받으면 패턴 파일을 각각 읽고 컴포넌트별로 나눠서 보고한다.

### 2. 점검 (기존 코드를 검사할 때)

공통 체크리스트 + 해당 패턴 체크리스트를 항목별로 검사한다.

- 코드 설명을 늘어놓지 않는다
- 항목별 **통과 / 실패 / 해당없음**과 **근거가 되는 줄 번호**만 제시한다
- 실패 항목은 수정 코드를 함께 제시한다
- 근거를 찾지 못했으면 통과로 처리하지 않는다. 실패다

### 3. 생성 (새로 만들 때)

공통 체크리스트 + 패턴 명세를 지켜서 작성하고, **작성 후 스스로 체크리스트를 돌려 결과 표를 함께 낸다.**

### 4. 보고 형식

```
## 점검 결과: TextField

| # | 항목 | 결과 | 근거 |
|---|---|---|---|
| 1 | 입력에 이름 연결 | ❌ | 187행 `<span>{label}</span>` — htmlFor 없음 |
| 2 | useId 사용 | ❌ | useId 호출 없음 |
| 3 | 메시지 연결 | ❌ | aria-describedby 없음 |
...

### 수정안
[실패 항목별 코드]
```

마지막에 **"직접 확인하는 법"** 을 덧붙인다. 사용자가 코드를 읽지 못해도 검증할 수 있도록, 검색할 단어를 알려준다.

## 공통 체크리스트

모든 컴포넌트에 적용한다.

| # | 항목 | 검사법 |
|---|---|---|
| C1 | 하드코딩된 색상값이 없다 (모두 디자인 토큰) | `#`, `rgb(`, `hsl(` 검색 |
| C2 | 임의값 대괄호 표기가 없거나, 있으면 주석으로 이유가 있다 | `[1`~`[9`로 시작하는 대괄호 검색 |
| C3 | 상호작용 요소가 키보드만으로 조작 가능하다 | `onClick`이 `<div>`/`<span>`에 붙어있는지 확인 |
| C4 | 포커스 표시가 보인다 | `focus-visible` 검색 |
| C5 | 스타일 때문에 바꾼 네이티브 속성이 없다 | `type=`, `role=` 검색 |
| C6 | 아이콘 전용 버튼에 `aria-label`이 있다 | `aria-label` 검색 |
| C7 | 장식용 아이콘/이미지는 스크린리더에서 숨겨진다 | `aria-hidden` 검색 |
| C8 | 컴포넌트 외부에서 `className` 오버라이드가 가능하다 | `cn(` + `className` 확인 |
| C9 | `forwardRef`로 ref를 전달한다 | `forwardRef` 검색 |
| C10 | 조합 제약(허용 자식·개수·맥락별 기본값)이 문서화되어 있다 | 주석 또는 별도 명세 확인 |

### C3 보충

`<div onClick>`은 키보드로 접근 불가능하다. `<button>`으로 바꾸는 것이 정답이다. 불가피하게 유지한다면 `role="button"` + `tabIndex={0}` + Enter/Space 핸들러가 **모두** 필요하며, 이 경우 실패로 보고하고 네이티브 전환을 권한다.

### C5 보충 — 가장 자주 걸리는 함정

시각적 재현을 위해 의미를 포기하는 결정은 대가가 크다. 특히:

- `type="password"` → `type="text"` + CSS 마스킹: 비밀번호 관리자·자동완성이 죽고, 엔진에 따라 마스킹이 아예 안 걸려 평문 노출 위험이 있다. **어떤 시각적 이유로도 허용하지 않는다.**
- `<button>` → `<div>`: 키보드·폼 제출이 죽는다
- 네이티브 `required` 없이 별표(*)만 표시: 프로그램적으로 필수가 아니다

## 개인정보 취급 필드

주민번호·카드번호·비밀번호 등을 다루는 필드는 추가로 확인한다.

- 플레이스홀더가 마스킹을 암시하는데 실제 값이 평문으로 보이지 않는가
- `autoComplete` 속성이 적절한가 (`current-password`, `new-password`, `cc-number` 등)
- 값이 불필요하게 DOM에 노출되지 않는가

불일치를 발견하면 시각 문제가 아니라 **보안 문제로 보고한다.**

---

## 규칙 확장

새로운 문제 유형을 발견하면 규칙을 추가한다. 추가할 때 반드시 **검사법을 함께 쓴다.**

검사할 수 없는 규칙은 규칙이 아니다. "시맨틱하게"가 실패하는 이유가 바로 이것이다.

패턴 파일이 없는 컴포넌트를 만나면, W3C WAI-ARIA APG(`https://www.w3.org/WAI/ARIA/apg/patterns/`)의 해당 패턴에서 **Keyboard Interaction**과 **WAI-ARIA Roles, States, and Properties** 두 절을 체크리스트로 옮겨 새 패턴 파일을 만든다.
